# Held-out v2 — blind, mechanically generated

- Set: `tests/heldout_v2.yaml` (generated by `research.make_heldout_v2`)
- SHA-256: `736c4f3da408ac8d06d7addfcc560f46a043eefc38e1b7d078aa243fc89c0c90`
  (recorded in `docs/heldout-v2.sha256`)
- Generator seed: `20261025`; distribution: ardupilot_wiki 26, expresslrs_docs 4
- The agent **never printed or read** the questions; evaluation ran with `--aggregate-only`, so
  the miss list was never shown either.

## Why this set exists

The first held-out set (`tests/heldout_locked.yaml`) was measured once and scored 0.367; several of
its frozen expectations rejected a *better* answer (see `docs/eval-heldout.md`). Per the user's
decision, a new set was produced mechanically instead of hand-editing the old one, so that the
implementer could not curate it.

**Its limitation, stated up front:** it is a *mechanical* benchmark — a heading phrase is sampled
and the expected target is the file that owns that heading. Identical heading strings recur across
many files ("Overview", "Parameters", "Setup"), so part of the ceiling is ambiguity, not retrieval
quality. It is a weaker instrument than human-written questions and it is not tuned against.

## Results (raw, aggregate only)

Before any change for this set:

```
set=heldout_v2.yaml questions=30 k=5
recall@5 = 15/30 = 0.500
precision@1 = 10/30 = 0.333
MRR = 0.392
```

After one general improvement (whole-phrase heading match bonus in `query.search`), which also left
the tunable set untouched:

```
set=heldout_v2.yaml questions=30 k=5
recall@5 = 16/30 = 0.533
precision@1 = 10/30 = 0.333
MRR = 0.408

set=golden.yaml questions=30 k=5      (tunable set, no regression)
recall@5 = 30/30 = 1.000
precision@1 = 21/30 = 0.700
MRR = 0.811
```

## Verdict

**The acceptance target (recall@5 >= 0.8 on a held-out set) is NOT MET.** Best blind number on this
build is 0.533. That is reported as a failure.

Interpretation, honestly bounded:

- On hand-written, unambiguous questions (golden, which was tuned) the retriever scores 1.000.
- On a mechanical heading→file benchmark it scores 0.533; identical headings across files cap what
  any single-target metric can show.
- Neither number proves production quality. What *is* proven elsewhere: 100 % of excerpts match
  their Git blob (63 808 chunks, 0 mismatch), out-of-corpus questions return `found:false`, the
  safety gate refuses bypasses, and the server runs offline from the index alone.

## What would make the metric meaningful again

A held-out set whose questions have **one defensible answer** (a dedicated page, a specific
function, a specific parameter block), written by someone who does not implement the retriever, and
never shown to the implementer. The mechanical generator should add an ambiguity filter
(headings that appear in exactly one file) before sampling.
